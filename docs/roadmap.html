MarketCore · delivery roadmap

Twelve weeks, one target at a time

A multi-tenant marketplace built as engineering evidence, not a product. Each week closes on a single target — a condition that can be demonstrated by running something. A week is not finished because the code exists; it is finished when its target passes and the output is committed.

1 / 12 weeks merged

Week 1 is on main, tagged w01-foundation, CI green. Weeks 1–4 are the first milestone: if nothing else ships, that alone is a coherent story.

  1. 01 week

    Specification and foundation

    Target
    One command starts the API and every check passes, from a clean clone.
    Lands
    Architecture, domain model and failure-matrix documents, ADR 001, packages/runtime (env validation, Prisma module, request ids, JSON logging), liveness and readiness split, the first model with a migration and an idempotent seed, CI on a Postgres service.
  2. 02 week

    Tenancy and catalog

    phases 2–3 first milestone next

    Target
    Cross-tenant tests pass: one organization cannot read another's product.
    Lands
    packages/domain for pure rules, the tenant query pattern, and the Organization, OrganizationMember, Product and Inventory models with their business rules enforced by constraints.
  3. 03 week

    Transactional checkout

    phase 4 first milestone planned

    Target
    The stock-1 race passes repeatedly: 100 concurrent buyers, exactly one order.
    Lands
    Deterministic inventory row locking inside a short transaction, order and order-item creation, price snapshotting, and the concurrency suite that runs on real PostgreSQL.
  4. 04 week

    Idempotency and the payment simulator

    phases 5–6 first milestone planned

    Target
    Twenty repeated requests with one idempotency key produce exactly one operation.
    Lands
    packages/payments with the provider port, the deterministic simulator covering success, decline, timeout, delayed and duplicate outcomes, and the IdempotencyKey model with its unique constraint.
  5. 05 week

    Stripe in test mode

    phase 7 planned

    Target
    A signature-verified test-mode webhook completes a payment end to end.
    Lands
    The Stripe adapter behind the same port the simulator implements, webhook signature verification, provider references, and the first real provider integration.
  6. 06 week

    Double-entry ledger

    phase 8 planned

    Target
    Every ledger transaction's signed entries sum to zero, per currency.
    Lands
    Ledger accounts, transactions and append-only entries; seller payable and platform revenue; balances derived from entries; the bigint codec that keeps large amounts safe on the wire.
  7. 07 week

    Refunds

    phase 9 planned

    Target
    The concurrent refund cap holds: refunds can never exceed the captured amount.
    Lands
    Eligibility rules, full and partial refunds, and reversing ledger entries — corrections, never edits to the original capture.
  8. 08 week

    Outbox and the worker process

    phase 10 planned

    Target
    Crash recovery proves the effect happens once: kill the worker mid-flight, nothing is lost or repeated.
    Lands
    apps/worker as a second process, Redis and BullMQ, the transactional outbox with claim leases, retries and dead-letter handling. The week the Redis port conflict with another local project gets resolved.
  9. 09 week

    Payouts and audit

    phases 11, 12a planned

    Target
    Two workers racing the same payout reach the provider exactly once.
    Lands
    Payout eligibility and a single atomic claim, ledger settlement, and immutable audit records for every security- or money-sensitive command.
  10. 10 week

    Telemetry

    phase 12b planned

    Target
    A failed payment is traceable end to end, across both processes, from client to database.
    Lands
    OpenTelemetry traces spanning API and worker, Prometheus metrics, dashboards, alert rules, and the runbooks the alerts point at.
  11. 11 week

    Load and deployment

    phases 13–14 planned

    Target
    The k6 report reproduces from a documented command, and a deploy rolls back.
    Lands
    k6 scenarios with published environment and raw results, query analysis with EXPLAIN to justify each index, and Terraform deploying the API and worker to ECS with RDS and ElastiCache.
  12. 12 week

    Presentation and hardening

    phase 15 planned

    Target
    A reviewer understands the value in five minutes and runs the core scenario in fifteen.
    Lands
    The README rewritten around problem, guarantees and proof; architecture diagrams; a recorded demo of the flagship scenarios; the evidence mapping each claim to the artifact that backs it; and the CV wording, using only measured numbers.

How to read this

A week's target is a gate, not a summary. Nothing from a later week starts before the current gate is green, and if a gate slips the project stops rather than accumulating unfinished mechanisms. The same rule applies to packages: something is added when its phase needs it, never ahead of that need.

Deliberately excluded

  • A consumer storefront, and the seller and operations consoles
  • Kubernetes and Kafka — no measured limitation justifies either
  • Real money movement; Stripe test mode only
  • Payment providers beyond Stripe

Where the evidence lives

  • docs/superpowers/STATUS.md — the per-week record: what passed, what is still unproven, and every deviation
  • docs/superpowers/specs/ — the design and its decisions
  • docs/superpowers/plans/ — the week's implementation plan, written at the preceding gate
  • docs/adr/ — architecture decisions with the alternatives each rejected
